# Novel Studio 架構決策

## 產品原則

1. 本機優先：沒有網路也能完整寫作。
2. 資料安全優先：自動儲存、快照、備份與復原必須先於 AI。
3. 桌面完整、手機聚焦：手機先服務快速記錄、閱讀、查詢與小幅修改。
4. AI 必須可核准：AI 只提出候選資料、問題與差異，不直接覆寫正文。
5. 跨平台但依序發布：Windows 先行，再驗證 macOS、Linux 與行動平台。

## 程式邊界

- `src/domain`：不依賴畫面的小說領域型別與規則。
- `src/storage`：專案儲存介面。目前由瀏覽器本機儲存實作，之後替換為 SQLite。
- `src/components`：可重用的工作區元件。
- `src/data`：開發及示範資料，不放正式使用者內容。
- `src-tauri`：Tauri 原生層，負責 SQLite migration；後續再加入檔案、備份、
  系統選單與更新。

## 目前儲存實作

- 瀏覽器開發模式：`BrowserProjectRepository`，資料保存在 localStorage。
- Tauri 桌面模式：`TauriProjectRepository`，資料保存在 `novel-studio.db`。
- 執行環境由 `createProjectRepository` 自動辨識，不由使用者手動切換。
- SQLite 第一版以完整 Project JSON 做原子性儲存，同時預留快照、附件與同步操作表。
- `.novel` 是含格式版本、匯出時間及完整 Project JSON 的可攜交換檔，匯入前會
  驗證資料結構與場景正文參照。
- 每日自動備份、手動快照、匯入前及還原前保護版都保存在目前裝置的快照儲存區。
- 多小說專案檔案選擇完成後，再把每部作品遷移為獨立 `project.sqlite`。

## schema v2：可增長的故事知識層

- 人物、地點、勢力、物品、世界規則與專有名詞都有不可變 UUID；顯示名稱與
  別名可以修改，不會破壞既有場景關聯。
- `SceneEntityLink` 使用角色欄位區分 POV、地點、參與者、提及與主題。
- `EntityRelation` 保存實體之間的方向、類型、說明及來源場景。
- Tag 本體與 Tag 指派分離，同一 Tag 可連結場景、世界觀實體或靈感。
- 靈感使用獨立 `InspirationItem`，可以先保持未定狀態；轉為場景時複製正文、
  Tag 與實體關聯，但不刪除原始構思。
- 舊 schema v1 載入後會自動轉換；舊版的 POV／地點文字會對應既有實體或建立
  待補充的實體，並在下一次自動儲存時寫回 schema v2。

## schema v3：雙軸故事時間

- `TimelineEvent` 同時保存故事內發生順序與敘事揭露順序，兩者可以獨立調整。
- 虛構曆法、模糊年代與相對時間使用 `storyTimeLabel`，不強迫轉成現實日期。
- 事件可連結多個場景及世界觀實體，作為後續年齡、行程與設定校對來源。
- schema v1／v2 專案載入時，會依 Binder 手稿順序替既有場景建立初始事件；
  確定性 ID 可避免重複遷移。
- 新增場景及靈感轉場景會同步建立事件，避免長篇內容增加後時間線漏失。

## schema v4：自包含研究素材

- `ResearchItem` 保存筆記、網址、PDF、圖片或文件的書目資料、摘要、工作筆記與
  場景／世界觀連結。
- 匯入附件轉為 data URL 嵌入 Project JSON，避免原始檔移動後失效，並確保
  `.novel` 跨電腦交換時能攜帶素材。
- 桌面版單一附件限制 15 MB；localStorage 容量較小，瀏覽器模式限制 2 MB。
- `.novel` 匯入上限提升為 100 MB，匯入時同時驗證研究素材連結。
- SQLite `research_items` 保存可索引的素材 metadata；目前完整 Project JSON 仍是
  原子儲存來源，後續可再把大型附件搬到內容雜湊資產目錄。

## Compile 與輸出邊界

- `compileProject` 依 Binder 階層與 `sortOrder` 組裝卷、場景及正文，不修改原始手稿。
- Compile 選項只影響當次輸出，可篩選稿件狀態，以及控制書名頁、卷／場景標題、
  摘要與場景分隔方式。
- DOCX 使用最小標準 OOXML 封裝；EPUB 使用 EPUB 3 OPF、導覽文件與 XHTML 章節。
- DOCX 與 EPUB 都使用內建無壓縮 ZIP 寫入器，測試時交由 Python `zipfile` 及
  XML parser 做獨立結構驗證。
- PDF 不以缺少中文字型的簡易 PDF 產生器輸出，而是使用專用 A4 列印 CSS 和
  Windows 系統列印視窗，確保繁體中文字型能被正確呈現。

## schema v5：可核准的本機分析

- `AiFinding` 保存穩定指紋、類別、嚴重程度、目標、來源引文、建議動作及審核狀態。
- 本機分析器讀取 Project 記憶體中的正文及結構化連結，不執行網路請求。
- 重新掃描以指紋比對結果；已接受或略過的決定會保留，不重複建立待辦。
- 可套用動作限制為場景摘要、人物屬性與場景實體連結，不能直接修改正文。
- 所有動作先顯示目前值與採用後結果；只有作者按下核准後才更新 Project。
- `ai-candidate` 來源會保留在場景實體連結上，讓後續稽核能辨識資料由候選流程建立。
- 未來接入語言模型時，供應器必須遵守同一 Finding 與核准介面，且在送出前顯示
  實際資料範圍。

## v0.8：全專案即時搜尋

- `buildProjectSearchIndex` 將目前 Project 記憶體轉成暫時搜尋文件，不建立第二份持久資料源。
- 索引涵蓋手稿正文與摘要、世界觀名稱／別名／屬性／關係、雙軸時間事件、研究來源、
  靈感、Tag 及已建立的跨模組關聯。
- 查詢採 Unicode NFKC 正規化與繁體中文不分大小寫比對；多個詞預設必須全部命中。
- 各欄位使用不同權重，名稱與別名優先於摘要及內文，完全相符再額外加權。
- 搜尋結果只保存導覽目標、上下文摘錄及命中欄位；不修改 Project，也不執行網路請求。
- `ProjectSearchResult` 是 UI 與未來 SQLite FTS／語意檢索後端之間的穩定介面，搜尋實作
  可替換而不必改動各模組的開啟流程。

## schema v6：快速收集與靈感附件

- `ResearchItem.linkedInspirationIds` 讓研究素材與靈感建立穩定 UUID 關聯；圖片及文件本體只
  保存於研究素材，不在靈感中複製 Data URL。
- `research_inspiration_links` 為未來將 Project JSON 正規化進 SQLite 所預留的雙向查詢表。
- 舊專案載入時會自動補上空的 `linkedInspirationIds`，不需要使用者手動轉換。
- 快速收集先以 MIME type、附檔名及 URL parser 做確定性分類；文字內容僅使用本機規則
  建議靈感類型，不執行網路請求或自動改寫內容。
- 附件以檔名、大小及 MIME type 做基礎重複檢查，網址以完整 URL 比對；重複項目會沿用
  既有素材並補上靈感關聯。

## 預定本機專案格式

```text
MyNovel.novel/
├── manifest.json
├── project.sqlite
├── assets/
│   ├── images/
│   ├── documents/
│   ├── audio/
│   └── references/
└── generated/
    ├── thumbnails/
    └── previews/
```

SQLite 是正式資料來源，素材檔依內容雜湊命名。備份檔存放在專案目錄之外，
避免備份包含備份本身。

## 同步原則

- 不直接同步開啟中的 SQLite 檔案。
- 每台裝置保存自己的本機資料庫。
- 同步服務交換帶有 UUID、裝置 ID、基準版本及時間的邏輯操作。
- 附件依雜湊上傳並去除重複。
- 同一場景發生衝突時保留兩版，不能靜默覆蓋。
- 確認多人共同編輯需求後，才加入 Yjs／CRDT。

## AI 邊界

- AI 只能讀取使用者選定或檢索出的必要內容。
- 人物資料擷取先寫入候選區。
- 一致性問題保留來源場景與原句位置。
- AI 修改必須顯示差異並經使用者核准。
- API 金鑰由作業系統安全憑證保存，不寫入小說專案。

## 驗收底線

- 中文輸入法組字不遺失。
- 程式意外關閉後可復原最近內容。
- 百萬中文字專案仍可正常搜尋與開啟場景。
- 備份可在另一台機器完整還原。
- 匯出不改變原始正文與專案排序。
- 同步衝突不造成任何一方內容消失。
